The shapes of batch jobs

We took the resource request from every script and wrote it as a Flux jobspec. That puts six workload managers in the same format, so we can count and compare them. There are – shapes.

What a shape is

The directives in a script turn into a small tree of resources. A slot holds one task.

#SBATCH --nodes=2
#SBATCH --ntasks-per-node=16
#SBATCH --cpus-per-task=2
#SBATCH --gpus-per-task=1
#SBATCH --time=01:00:00
node[2] > slot[16] > core[2] + gpu[1]
duration 3600

How shapes are grouped

Here is the shape above at four levels of detail. A * means the script didn't give that number.

Exact
node[2]>slot[16]>core[2]+gpu[1]
Binned
node[2]>slot[9-16]>core[2]+gpu[1]
Totals
groups[2] tasks[17-32] cores[33-64] gpus[17-32]
Topology
node>slot>core+gpu

Use totals to compare managers, since they don't depend on how each one writes a request. A group is a node, or a chunk in PBS.

Percentages are of repositories unless we say otherwise. A repository with 5,000 scripts counts the same as one with a single script. Built –.

What runs in which shape

We pull program names out of each script with simple rules: whatever follows srun or mpirun, other commands, and anything in a module load. No model is involved and names are left alone, so gmx and gmx_mpi show up separately.

Caveats

  • We haven't checked the jobspecs with Flux yet.
  • Flux, OAR and Cobalt have 200 repositories or fewer each, so don't read much into their numbers.
  • We don't read PBS requests like -l ncpus= yet, so some PBS scripts look like they ask for nothing.
  • PBS ngpus and LSF -gpu num= mean different things at different sites. We treat both as GPUs per chunk or host.
  • If people copy a template and tweak it, each copy counts as its own repository.
  • Program names are messy. Shell functions and stray words get picked up. Trust the common names more than the rare ones.
